05One metric, well documented

Three different numbersbecome one.

94.1 · 96.0 · 92.4 → 92.4%. The card says why.

OTIF %Metric card
What it is
Orders that arrive on time and in full, over orders delivered.
Grain
One order, not one line: by line it gave 96.0%; by order, 92.4%.
Filters
Only orders delivered from the 3 warehouses; transport costs, out.
Logic
“On time” = received by the customer on the promised date. Customer service’s definition wins, not Logistics’.
Owner and rhythm
Operations management · checked every Monday · target 94%.
OTIF % = DIVIDE ( [OTIF orders], [Orders delivered] )

06Where it lives

Next to the code,not in a separate wiki.

07With AI, and how I check it

AI writes fast.I answer for every word.

  1. 1

    AI writes the draft

    Claude Code reads the repo; the Power BI Authoring MCP server writes the model descriptions.

  2. 2

    I compare it with the code

    Formula, grain and filters, one by one. If it doesn’t match, it gets fixed.

  3. 3

    A test flags what’s missing

    dbt-project-evaluator and the “Visible objects with no description” rule.

  4. 4

    It’s reviewed in Git

    Every documentation change goes through the pull request diff.

✕ Never personal data in the chata description without reading the measureone AI checking another: it doesn’t match human judgment

08Common mistakes

Bad documentationis worse than none.

  • ✕ A separate wiki nobody updates→✓ Next to the code, reviewed with every change
  • ✕ The same metric defined in every dashboard→✓ Once, in the model
  • ✕ Documenting everything→✓ What’s used, by risk
  • ✕ Accepting what AI writes→✓ Human review against the code
  • ✕ Describing the how→✓ Explaining the why and the exception
09How I know I’m done
